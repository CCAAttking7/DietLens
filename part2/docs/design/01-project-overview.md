# 项目复核与重设计范围

版本 R2-P0 · 2026-11-17 · 状态：2026-11-17 用户“那就方案B”确认本阶段范围。

## 1. 项目与作业目标

DietLens 面向成年人的日常饮食决策、准备、记录与微习惯支持。使用场景包括食堂、外卖、便利店、居家；用户已确认的目标、预算、过敏、忌口和授权可复用。Agent 帮助理解任务与组织候选，确定性业务服务维护约束、数量和状态。

作业二应交付能够指导实现的设计：逻辑、部署、技术架构，领域与交互模型，关键取舍及理由，需求变更、UI/UX、风险验证、工具反思、注释参考文献、成员贡献。原要求文件仍位于 part2 根目录。保持“可解释、用户确认、状态独立、可恢复”的业务主线。

## 2. 已有材料与可用能力

作业一 SRS 为需求基线，14 个用例和 20 项功能需求均保留。旧稿已提取 26 项 NFR、十项细化、十项代码差距，制作十张架构/领域/流程图和七张静态界面示意。当前代码为 React/TypeScript + FastAPI/Python 模块化单体，具有 Harness、独立领域服务及 SQLite/Postgres 适配。

旧稿的图形表达及契约深度还需补强；现有 API 和数据结构作为现状证据，不自动成为目标设计。既有测试记录保留日期、提交和环境，不作为新设计验证结果。

## 3. 业务主线保持不变

1. 食品/菜单信息进入后，形成有来源和未知字段的候选，核对关键事实后作约束内选择。
2. 未来计划、准备采购、基础库存、个人实际餐食是独立事实，可按对象及版本显式关联。
3. 微行动有线索、行为、努力量和依据；采纳、跳过、执行自述、未知分别保存。
4. 回顾读取已授权且有效的业务事实，标注期间、来源、分母和未知；不反写事实。
5. 每次恢复重新检查当前授权和约束。确认写入有明确对象、版本和结果，重复提交不创建重复事实。

## 4. 重设计方案比较

| 方案 | 收益与代价 | 本轮建议 |
|---|---|---|
| A 只换图表工具与外观 | 快速，但无法补足字段、约束、API 和状态守卫 | 不作为本轮重设计范围 |
| B 在原范围内补齐领域、架构、数据、接口、交互与一致性 | 复用已有业务证据，逐层形成可实现模型；需要阶段确认及契约校验 | 推荐 |
| C 重定产品定位及技术栈 | 能探索不同产品，但增加需求变化和实现迁移，脱离当前作业连续性 | 暂不采用 |

建议选择 B。工具的职责是使模型可编辑、可校验、可追踪；是否增加组件由实际业务和质量属性决定。数据库、API 和开发任务设计作为作业的支撑证据，最终正文保留关键部分，控制报告篇幅。

## 5. 已知约束与未决项

| 项目 | 当前处理 |
|---|---|
| 输出范围 | 仅 part2；新稿放 part2/docs/design，API/SQL 等放 part2/api、part2/database |
