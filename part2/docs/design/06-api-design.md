## 2. 接口边界与14个用例

查询不写业务事实，分析只产生候选，确认命令才建立或修订对应事实。任务进度、上传图片和未确认候选可按临时期限保存，不计作已购、已吃或行动完成。所有业务变更均先预览再确认；不为每张数据库表开放通用CRUD。

| 用例 | 入口与主要契约 | 明确边界 |
|---|---|---|
| UC-01 档案管理 | profile、profile.confirm、calibration.answer | 确认目标、偏好、预算及硬约束；校准可跳过 |
| UC-02 食品核对 | media、analyses/food、food.confirm、foods、sources | 逐字段核对，上传不等于同意外传 |
| UC-03 营养比较 | analyses/comparisons | 同口径才算，缺值和无法换算独立说明 |
| UC-04 现实菜单 | analyses/menus | 配料、预算、价格时效和可获得性分别复核；无可靠候选可停止 |
| UC-05 日周计划 | analyses/plans、plan.confirm、plans | 完整模式3/21餐，指定模式只验所选集合；缺口仍是草案 |
| UC-06 准备采购 | preparation-preview、preparation.confirm/status | 按人数与兼容单位汇总；已购与已准备互不代写 |
| UC-07 个人记餐 | meal-prefill、meal.confirm、meal-records | 个人份量默认待核对，至少一项食物；同槽可多次用餐 |
| UC-08 期间回顾 | reviews、expected.confirm、recovery.confirm、week.present | 事实、分母和冻结决定分别处理 |
| UC-09 生成调整微行动 | analyses/actions、actions | 候选含线索、行为、努力量及依据；替代重查限制 |
| UC-10 行动决策与执行反馈 | action.decide、action.feedback、action.window | 采纳不计完成；原行动修订，窗口与执行日期分别保存 |
| UC-11 恢复任务 | tasks、command-receipts | 先查当前权限、期限和提交结果；不盲目重做 |
| UC-12 确认当前情境 | contexts、context.confirm | 复用档案，仅核对会影响当前选择的缺口 |
| UC-13 数据控制 | consents、data.export/delete/renew、data-jobs | 受理与完成分开；删除退出处理不靠旧回执恢复 |
| UC-14 人工库存 | inventory.confirm、inventory、ingredient.confirm | 原值新值及原因先预览，未知不是零，无隐式扣库 |

档案、校准、交互开关分别有本人查询与确认类型。标准食材若尚不存在，先形成任务内匹配候选，再确认持久身份；不从名称匹配推断完整配方。最终页面与导航在P6确定，此表表达用例入口。

## 3. 统一预览与提交

### 3.1 第一次写入

1. 创建本人任务，取得服务端任务身份、草稿修订和最长7天的任务截止。任务创建请求的client_request_id只用于临时创建去重，不是业务提交键。
2. 读取当前资源，必要时进行文字或图文分析。每步仍受工具3次、模型2次、只读瞬时重试1次及15秒总截止；周计划至多3步/45秒。没有计费配置不发付费调用。
3. POST /command-previews发送明确类型的intent、所见草稿修订和版本守卫。服务端校验本人归属，补齐当前授权、关联版本、受影响槽位、清单和库存等依赖。修改已有对象缺少所见版本时拒绝，不静默把旧稿当最新内容。
4. 有缺口返回待核对预览及原因，不签发operation_key和confirmation_token。可确认时返回完整内容、具体影响、版本守卫、摘要及服务端操作标识。编辑任一内容都须重新预览。
5. 用户核对并明确确认后，POST /commands只发送原预览身份、草稿修订、摘要、令牌和decision=确认；Idempotency-Key必须为原预览签发的键。该请求不允许夹带新业务内容或自报user_id。
6. 首次提交重新检查任务/预览期限、当前许可、删除状态、草稿、来源、约束和预期版本；同库写入业务、任务进度、事件和回执。任一失败整体回滚。

确认预览最长15分钟，且不超过任务、材料或证据允许的期限；超时后重新展示差异再核对。这是确认页面的技术有效期，行动结束时间仍按具体行动提出并由用户确认，不采用统一行动时长。

摘要由服务端对规范化内容、依赖和影响生成；客户端只原样回显，不把客户端自报哈希当作已核对内容。确认令牌不授予额外权限，当前用途和主体检查始终优先。

### 3.2 重复提交与响应丢失

同一用户和操作键唯一。同键同请求摘要在当前允许范围返回原commit_id，replayed标为真；同键异内容返回冲突。服务器先核验当前身份和已提交回执，再区分重放与首次提交；已提交回执不会因原任务或预览到期被误作新写入。

客户端收到网络错误或结果待核对时，先GET /command-receipts/{operation_key}。404只说明当前未查到可返回回执，不证明业务从未提交；数据库不可用仍保持待核对。只有确认未提交、原任务/预览有效且绑定未变时，才按原键重试；不能新造键重做。

任务7天到期时可解除回执的临时任务引用；回执最长180天且受主动删除约束。回执到期后，原任务已经失效，旧确认只能被拒绝。原回执只返回必要身份和版本引用，并重新检查对象有效性；redacted说明原结果已因删除或授权变化隐藏。

## 4. 版本与数据形状

| 字段或类型 | 含义与来源 |
|---|---|
| ResourceVersion.version | 并发守卫；0仅表示新建目标尚不存在。身份对象通常对应row_version，档案/用途/偏好/预期周对应其当前修订 |
| FactReference.revision | 内容来源修订，例如原餐食版本或执行修订；不能拿并发版本替代 |
| VersionReference | 已知类型上下文中的身份与内容修订，例如清单所引用的计划 |
| draft_revision | 任务内临时核对版本，任务编辑或新候选会使旧确认失效 |
| authorization_epoch | 当前用途控制修订；历史快照不是现时许可 |
| snapshot_revision | 同一用户数据截点，变化时重算或刷新，不拼接不同截点的分子分母 |

食品证据和确认情境按不可变身份引用，固定内容版本为1。学习候选在P4未另设行版本，读取时以当前用户data_revision作保守并发守卫；不虚构不存在的物理版本列。计划槽位替换也须推进受影响旧计划身份的row_version，旧版确认内容保持不变。

数量采用已知/未知联合类型。已知值为实际值×1000000的整数并带单位，未知分支禁止带amount_micros；未知库存也必须有核对口径。内部换算不提前舍入，最后显示按需求保留一位小数。名称、规格、配料、营养基准、价格基准、币种及字段来源分别解释；营养100g基准不能套用到每份价格。

一次个人餐食的foods至少一项。计划预填只返回名称、明确来源和待核对份量，不保存实际记录。计划查询同时返回计划餐次和食物的持久来源标识，供预填及后续关联使用。只读准备草案返回具体需求身份及库存截点，不伪造已保存清单身份；确认时校验用户所见库存截点。清单以明确的完整确认计划版本为来源：该版若已部分被替换，先展示剩余与替换范围并确认相应新计划版本，再生成新清单；不能静默把残存槽位当成原版本或把旧清单改写成当前值。

OpenAPI能限制分支、字段、范围和格式；日期先后、完整3/21餐、所选槽位集合相等、至少修改一项的业务含义、仅采纳后反馈、依据仍有效等仍需用例规则校验。不能用“结构合法”代替“业务可提交”。

## 5. 身份、用途和材料

除最小health接口外，所有业务接口要求本人身份令牌。托管端验证签发方、受众、期限和主体；本地演示仅显式离线配置，认证失败不回退。资源属于他人时统一404，不返回当前版本、差异或存在性；写入、查询、恢复和结果发送前分别检查当前允许范围。

上传JPEG/PNG仅保存本地核对材料，技术上限10MiB；服务端还须在解码前检查尺寸及配置的解码预算。超限或低质可裁剪、重传或手输。上传键在任务内按内容摘要去重，不使用业务确认键。外部解析前另检查逐图、用途、接收方及24小时期限；本地看图不代替外传许可。

GET /media/{asset_id}/content允许本人在有效期内重新核对原图，不返回内部文件键。文件或授权已到期即拒绝读取；候选、日志和来源说明不保存可恢复原图的副本。来自用户、来源或模型的文字都是数据，不能指定任意工具、修改系统权限或伪造用户确认。

所有个人响应声明Cache-Control: no-store。服务端不记录原图、完整档案、令牌或下载凭证；诊断仅用请求标识、错误类别和必要元数据。接口频率及解码容量配置留P7实测，但调用次数预算和停止边界沿用已确认需求。

## 6. 导出、删除及受理状态

导出和删除走同样的预览与确认。提交成功返回Receipt，只说明命令已经提交及job_ids已建立，不表示文件生成或清理完成。GET /data-jobs/{job_id}分别显示待处理、处理中、已完成、失败；已完成必须有completed_at，失败须有可理解的范围和原因。

导出只通过认证下载接口提供UTF-8 JSON文件，不公开无认证URL或内部存储键。导出文件最长24小时，过期或主动删除后立即不可下载。文件覆盖本人仍在允许范围内的对象、版本、来源及必要解释；未知和已清理状态原样说明，不补造历史。

### 全量删除后如何核对结果

如果提交响应丢失，而删除又清除了本人身份映射，单纯依赖旧回执会让用户无法分辨未受理、已完成或查询失败。本阶段补充一个仅限本次删除进度的技术机制：

- 可确认的删除预览先返回预分配job_id和deletion_status_access，用户提交前即可保留。确认动作仍使用原operation_key，进度凭证不能触发删除。
- 凭证绑定原已验证身份主体、任务身份、范围与期限，最长7天；查询还须同主体有效身份令牌。普通本人映射存在时可用常规路径，映射清理后只凭此组合查看本次最小进度。
- 该例外只适用于GET /data-jobs/{job_id}，不允许读原事实、下载文件或查看其他任务。未提交前查询返回404；客户端不能把404当完成。
- 进度任务只保留处理状态、时点和必要计数，清空原敏感范围内容；status_access_expires_at作为清理断点元数据保存，不新增业务表。到期清除这份最小状态，凭证失效后410表示不可再查询，不恢复数据。

这补充了P4数据控制任务的保留细节：用于本次查询的最小任务状态最长7天；备份抑制标记仍按相关备份最长30天到期，二者用途分开。主动删除仍须立即停止新处理并在24小时内退出相应在线处理，进度凭证不延长原业务数据期限。

## 7. 错误、分页与降级

错误使用application/problem+json，包含稳定code、中文title/detail、HTTP状态、request_id、commit_state和retry_strategy。完整映射见[错误目录](../../api/error-catalog.md)。

| 情况 | 客户端行为 |
|---|---|
| 401 | 重新登录，不回退到演示身份 |
| 403/404 | 说明当前不可访问，不展示其他主体的字段或猜测存在性 |
| 409 版本/草稿变化 | 展示允许范围内差异，重新核对；不自动覆盖 |
| 409 同键异内容 | 停止复用；确需新操作必须先重新预览 |
| 410 预览/任务/材料到期 | 按对象期限重新核对或停止，旧材料不可复活 |
| 422 | 指明字段和业务缺口，保留已确认资料 |
| 429 | 按已知Retry-After等待，或明确预算用尽后改手动；不无限重试 |
| 503/网络错误且结果待核对 | 先查询原回执，不以新键重做 |

列表默认每页20、最多50，使用绑定本人、过滤条件和数据截点的不透明游标。业务列表可携带snapshot_revision复用回顾截点，数据变化返回冲突并刷新。临时任务列表固定创建截点及排序键，进度按当前状态更新，并排除当前过期任务；不宣称跨页冻结了草稿状态。

行动列表带日期过滤时须明确date_basis：执行日期用于完成事实，窗口结束日期用于结束队列；as_of可固定到回顾统计时点。不能按创建日或报告日过滤替代这两种口径。计划列表按当前有效槽位与期间是否相交筛选，实际餐食按当前修订的业务日期筛选。

回顾按单一读快照计算，发送前再次检查当前授权。长期间跨多个自然周时，各周取最大已确认预期版本；任何所需分母未确认或不可得，整体覆盖保持未知，并解释已知范围。来源摘录超限时has_more_sources为真，完整来源通过同截点分页查询，不静默把摘录当全部来源。

分析返回可核对、部分结果或已停止。无结果时省略result并说明原因，不能返回结构空壳充当成功。食品关键证据缺失阻止相关推荐，其他可用查询或手动输入可继续。模型不计算权威分母，也不直接调用确认提交入口。

## 8. 兼容现有项目

当前api_server.py有/api下按任务、计划、快速记餐、库存等分散的确认和直接写入路径。新契约是目标/api/v2，不宣称当前代码已支持。未来迁移时旧路径只能委托同一预览/命令策略或明确停用，不能保留绕过统一事务与确认的第二条写入路径。

查询不再通过路径中的任意user_id选择主体。旧的单食物餐食输入需转为一份餐食的foods数组；兼容适配也必须展示个人份量核对。旧API是否保留及停用周期在P7实施计划确定，不把新设计文件当成兼容性已经验证。

## 9. 已执行验证与后续验收

OpenAPI由openapi-spec-validator校验；40个虚构正反例由OpenAPI结构校验器接受或拒绝，覆盖未知/零、空餐食、同餐多食物、客户端自报用户、修改确认内容、未注册命令、空回答、删除范围及六种分析结果。全部本地引用可解析，操作标识唯一，路径参数和主要表映射齐备，20项FR不依赖统一提交入口的兜底编号补足覆盖。

本地Swagger Editor实际导入契约，保留原示例备份并导出JSON。最终导出与权威契约一致；最终画面显示中文标题及分组，未发现错误或警告行。规范校验记录独立保存，不以“编辑器能打开”代替规范合格。

当前没有发业务HTTP请求、导入产品服务、创建业务库或执行迁移。并发双提、授权竞争、提交后断网、数量换算、窗口重算、真实文件清理和删除状态凭证的范围隔离，仍须在P7形成服务级验收任务。

## 10. 待确认与下一步

本阶段新增技术取舍：查询/分析与确认分开，封闭的23类业务命令，最多15分钟的确认预览，有界分页，删除前先行签发的仅进度查询凭证，以及清单来源版本被部分替换后先确认整合范围。它们不改变完整/指定计划、多人准备与个人实际、同一行动反馈修订等已确认规则。

确认P5后进入P6，先展示中文用户流程、信息结构和视觉方向供确认，再制作可编辑交互原型。具体校准题库、排序参数及技术容量配置仍留对应阶段确定；本次不填造题目、算法参数或部署结果。
