【幻灯片6】
05 · 决策
关键设计决策（ADR）
DietLens · 系统设计汇报
6
D1 应用形态：模块化单体
选择：React 客户端 + 单个 FastAPI 服务 + Python 领域模块
理由：小团队、单一部署单元、便于本地集成测试
代价：共享发布与故障域；需独立扩展时再拆分
D2 演示持久化：SQLite
选择：API 主机上的 SQLite 文件
理由：无需云账号，可复现本地演示与事务测试
代价：单机使用；多用户部署需显式共享库
D3 模型边界：解释与执行分离
选择：模型只做意图理解与解释；候选、约束与写入由确定性服务完成
理由：安全规则、计算与业务状态需可复现
代价：用户步骤更多，需衡量完成与纠错负担
D4 食品数据：来源候选
选择：可溯源的外部/本地来源，未知关键字段要求确认
理由：来源覆盖与新鲜度各不相同
代价：不承诺完整目录，扩推荐前先测覆盖
质量属性：安全与状态一致性 > 可维护性 > 性能 —— 确认门与幂等/版本 · Repository 隔离与模块化单体 · 单机 SQLite 与只读缓存

【幻灯片7】
06 · Agentic
Agentic 设计：Agent / Harness 与护栏
DietLens · 系统设计汇报
7
三层职责分离
Agent（模型）：意图理解 · 结构化字段 · 解释与回复
Harness：任务路由 · 工具白名单 · 调用上限 · 幂等键 · 确认门 · 事件记录
确定性业务层：候选生成 · 约束过滤 · 软偏好排序 · 单位换算 · 状态统计
边界：模型输出经 Schema 校验，不执行权威写入
自主性分级（护栏落到确认门）
可自主：已授权读取、只读检索、确定性换算、约束检查与解释
必须确认：目标 / 约束 / 计划 / 库存 / 餐食 / 行动决策 / 偏好规则、图片外传、删除
停止交接：关键事实未知、来源冲突、数据过期、约束冲突、医学请求、预算或时限耗尽

【幻灯片12】
11 · 风险
开放问题与风险（Part III 验证）
DietLens · 系统设计汇报
12
待原型验证的 5 个问题
1.  
计划预填后，用户能否区分「计划餐」与「实际记录」？
2.  
过敏 / 配料未知时，用户是否理解「先核对再推荐」？
3.  
模型失败后能否手动继续，且不丢任务、不误写？
4.  
代表性本地食品查询中，可用且新鲜的来源与关键配料字段占比？
5.  
写入成功但任务状态更新失败时，重试是否得到一致结果？
仍开放的设计风险
•  
业务写入与任务状态不一致（需事务 / 幂等重试）
•  
SQLite → Postgres 迁移未验证：事务、并发与跨用户一致性需在 Part III 验证
•  
食品源覆盖不足或过期，影响推荐可信度
•  
UI 证据口径不一致（需统一 run 表）
•  
工程测试 ≠ 用户证据（需真实任务研究）
