## 2. 版本差异处理

旧汇报将产品描述为更集中的 Harness 控制链路，并将单日计划作为当时的范围。当前 main 的设计基线指出：微行动有完整 Harness 流程；计划和快速记餐通过独立服务写入并关联任务；食品查询、综合回顾走专用路由。原 SRS 仍要求日计划和周计划。

本次以原 SRS 确定应设计的范围，以当前 main 代码确认已有实现。旧分支的范围缩减作为历史设计观点，不替代原始需求。每张正式图标注“当前实现”或“目标设计”；接口未经代码核对不标为已实现。

## 3. 当前架构事实

- 系统采用模块化单体：React 网页、FastAPI 服务、Python 领域模块。
- 本地演示使用 SQLite；仓库含 Postgres/Supabase 适配及认证路径。
- 模型用于结构化理解与表达；硬约束、数值和写入由确定性代码处理。
- 微行动候选、采纳与反馈由 Harness 编排；计划和记录有独立业务服务。
- 计划与实际餐食独立建模；任务状态表达交互进度。
- 当前食品资源包括外部查询和中国食物编码资料；编码索引的用途需与营养事实分开。

以上为源文件和设计基线检查结论。本轮没有运行应用、浏览器验收、负载或用户实验。

## 4. 本次必须回答的设计问题

| 决策主题 | 需要比较的方案 | 评价依据 |
|---|---|---|
| 应用结构 | 模块化单体 / 微服务 | 团队规模、事务边界、维护和部署成本 |
| 数据存储 | 本地 SQLite / 托管 Postgres | 演示可复现、并发、多用户隔离及运维 |
| Agent 自主性 | 受控状态机 / 开放式模型循环 | 安全、可恢复性、调用预算和用户控制 |
| 业务事实 | 独立业务对象与显式引用 / 由对话或计划推导事实 | 版本一致性、审计与统计正确性 |
| 写入一致性 | 同事务 / 幂等命令加对账 | 同存储内原子性、中断恢复与重复写入 |
| 食品资料 | 多来源带证据 / 单一来源直接采信 | 关键字段完整性、时效与核对负担 |
| 记忆 | 确认事实、任务临时态、待确认偏好分层 / 对话全文作记忆 | 授权、来源、删除及上下文成本 |
| 异常与成本 | 有界重试和手动降级 / 自动持续尝试 | 可用性、费用上限和状态诚实 |

每项决策记录包含：问题与驱动需求、备选方案、选择及理由、代价、受影响模型、第三部分 验证和重审条件。

## 6. 风险与验证种子

| 风险 | 待验证问题 | 计划证据 |
|---|---|---|
| 业务保存与任务更新分离 | 任一写入点失败后是否得到唯一一致结果 | 故障注入、操作回执、对象/事件快照 |
| 云库故障降级本地 | 托管部署是否会形成两份权威数据 | 强制云库失败，检查可见错误与写入停止 |
| 配料与食品数据缺失 | 用户是否理解待核对原因，来源是否足以支持候选 | 代表性查询字段覆盖率、理解问题 |
| 计划被理解为实际 | 预填和确认是否容易混淆 | 任务完成、误写次数、解释性提问 |
| 模型依赖失败 | 用户能否手动完成且恢复原任务 | 依赖故障任务研究和状态检查 |
| 历史测试范围混用 | 报告是否将旧环境结果表述成当前验证 | 每次运行记录提交、日期、环境、流程和结果 |
