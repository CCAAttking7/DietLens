# DietLens 产品逻辑与 Agent 编排模型

## 当前问题

DietLens 目前的 Harness 对 `micro_action` 任务保护得很好，但产品入口都被压进了同一条路径：

```text
描述一餐 → 核对情境 → 选择行动 → 反馈 → 回顾
```

这条路径适合“我现在需要一个小行动”，不适合所有用户行为。真实用户还会直接记录刚吃过的东西、修改昨天的记录、复用常吃餐、安排未来几天、查一个食品、回看某类阻碍，或中途从计划切换到记录。

因此，Harness 不应该只做线性状态门禁，而应该成为跨业务对象的编排控制面。模型负责理解意图和组织语言，Harness 负责恢复任务、选择只读工具、确认写入、保存事件和保证事实一致。

## 用户任务类型

### quick_log：快速记录

触发例子：

> 刚吃完一碗番茄面，份量不确定，帮我记下来。

处理方式：

1. 推断日期和餐次，但允许用户修改；
2. 建立 `MealRecord` 预览；
3. 份量未知保持 `null`，不补成零；
4. 用户确认后才写入实际餐食；
5. 不创建微行动，不要求等待反馈。

### micro_action：当前一餐的下一步

触发例子：

> 午餐有鸡肉饭和番茄面，帮我选一个简单的。

处理方式保持现有闭环：情境 → 候选 → 用户选择 → 执行反馈。它是 DietLens 的陪伴模式之一，而不是唯一模式。

### plan：未来安排

触发例子：

> 帮我安排明天的午餐，预算 30 元，最好不用复杂准备。

Harness 应读取预算、库存、既有计划、用户确认过的偏好和食品来源，再生成多个可比较方案。保存计划、生成采购清单和实际餐食记录必须保持对象分离。

### explore：食品资料与解释

触发例子：

> 这个燕麦适不适合我？

这是只读任务。来源、配料、过敏原、营养缺失和价格未知必须分开展示。资料不完整时只能进入 `needs_confirmation`，不能被模型表达成安全结论。

### reflect：回顾与调整

触发例子：

> 我最近晚餐总是没做到，问题可能在哪里？

Harness 应聚合计划、实际餐食、行动反馈、障碍备注和时间范围，输出：

- 已发生的事实；
- 仍然未知的部分；
- 重复出现的情境；
- 可尝试的调整路径；
- 需要用户确认后才能写入的偏好信号。

## 统一任务容器

未来的任务对象应显式保存：

```text
task_type: quick_log | micro_action | plan | explore | reflect
intent: 原始用户意图和结构化实体
parent_task_id: 从哪一条任务进入
resume_point: 当前可恢复位置
context_snapshot: 当时使用的档案、授权和数据版本
pending_writes: 等待用户确认的写入
linked_objects: 关联的计划、餐食记录、行动和资料观察
```

这样用户可以在一个任务未完成时切换到另一件事，系统保存当前上下文，之后从原位置恢复，而不是要求用户重新开始。

## Harness 的新职责

### 1. 路由

模型只输出结构化意图：任务类型、实体、缺失字段和置信度。路由结果不能直接产生写入。

### 2. 编排

根据任务类型选择工具组合。例如：

```text
quick_log  → profile.read → meal_record.preview → user.confirm → meal_record.confirm
plan       → profile.read → inventory.read → food.read → plan.preview → user.confirm
explore    → profile.read → food.search → assessment → user.inspect
reflect    → review.read → obstacle.aggregate → suggestion.preview → user.confirm
```

### 3. 恢复与切换

任何等待确认、等待反馈或外部资料失败的任务，都必须可以恢复。新任务不能覆盖旧任务，旧任务也不能阻塞新任务。

### 4. 事实边界

模型可以解释候选，但不能决定安全、数值、版本、授权和写入。所有业务写入继续通过确认门、版本检查和 operation key。

### 5. 记忆分层

- 事实记忆：用户确认过的目标、预算、过敏和授权；
- 情境记忆：某种时间、餐次和可选项下发生过什么；
- 偏好信号：多次反馈后产生的待确认线索；
- 临时状态：当前草稿、任务位置和未完成操作。

### 6. 证据状态与可追溯性

回顾不能把推测写成事实。计划与实际餐食在时间线上使用四种状态：

- `matched`：实际记录明确关联了 `plan_item_id`；
- `same_slot`：日期和餐次相同，但用户没有明确关联计划，只能标记为待核对；
- `unplanned`：有实际记录，但没有对应计划；
- `planned`：有计划，还没有实际记录。

每条用户任务还保留事件轨迹。前端只向用户展示可理解的步骤，例如“确认了餐次”“记下了选择”“保存了反馈”“修正了反馈”，过滤模型内部调用。用户可以在完成后展开查看轨迹，也可以修改反馈；修改会追加历史，不会覆盖事实或创建重复行动。

### 7. 跨入口连续性

首页、设置、计划和回顾都可以恢复未完成任务。首页优先提示最近一条未完成的 `micro_action`；设置页可恢复快速记录和计划；回顾时间线可以一键按计划预填实际餐食。所有入口都回到同一个 Harness 任务，而不是复制一套局部状态。

提醒是可选的节奏工具：只有用户开启 `reminders` 授权且行动进入退避窗口后才显示“稍后提醒我”。提醒不会改变完成状态，也不会自动提交反馈。

## 用户体验原则

记录类产品的核心不是让用户每天完成一张表，而是降低记录、复用和回看的成本。首页应该同时提供：

- 我刚吃完，快速记下；
- 我现在要决定吃什么；
- 我想安排之后几天；
- 我想查一个食品；
- 我想看看最近发生了什么。

用户可以从任一入口开始、暂停、切换、恢复、修改和复用。没有记录不应被当成失败，未知也不应被伪装成零或安全。

计划、实际和反馈在界面中分别呈现；记录实际餐食时可以明确关联计划餐次，也可以保留为计划外记录。回顾不是只读报表：Agent 线索提供“去记录一餐”或“开始一次新的尝试”等下一步入口，用户始终确认后才推进任务。

## 实施顺序

1. 保持现有 `micro_action` 闭环不变，增加统一 `task_type` 和任务恢复协议；
2. 将快速餐食记录接入统一任务路由，支持自动餐次、重复记录和编辑；
3. 将计划、食品探索和回顾变成可恢复的只读/确认任务；
4. 增加历史复用和待确认偏好信号；
5. 最后再引入图片、健康设备和更复杂的营养估算。
