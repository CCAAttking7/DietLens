# DietLens 产品定位与路线图

## 建议的短期定位

DietLens 当前最适合被定义为：**轻量、由用户控制的个人餐食决策与回顾伴侣**。它把用户确认过的饮食边界、眼前的一餐、实际吃过的记录、计划和行动反馈连在一起；它不会从餐名猜测营养，也不会把未确认的信息写成事实。

## 两个产品方向

| 方向 | 核心价值 | 当前架构匹配度 | 主要新增依赖 |
|---|---|---:|---|
| A：餐食决策与回顾伴侣 | 边界确认、低摩擦记录、单日计划、行动反馈、证据化回顾 | 高 | 更好的情境记录、可确认的偏好信号、计划与实际的关联 |
| B：营养追踪助手 | 逐餐成分、份量归一化、热量和宏量营养素覆盖 | 低至中 | 成分级餐食模型、可信食品来源、份量标准化、每个推导值的来源和不确定性 |

短期建议选择方向 A。现有的 Harness、显式确认、Plan/MealRecord 分离、反馈历史和 deterministic review 已经为方向 A 提供了完整边界。方向 B 需要把一餐可靠地链接到成分、份量和来源，在此之前显示热量总计会制造虚假的精确感，因此本轮不实现营养计算引擎。

## 能力状态

| 能力 | 状态 | 说明 |
|---|---|---|
| 饮食边界 | 已实现 | 过敏信息区分未知、明确没有、已记录；绝对忌口硬过滤，软偏好只影响排序 |
| 当前餐食决策 | 已实现（有限） | 根据用户输入的餐名和选项生成可解释的小行动；不做菜品成分级验证 |
| 实际餐食记录 | 已实现 | 与计划分离，份量未知保持未知 |
| 单日计划 | 已实现 | 当前界面明确是单日；多日 API 能力暂不在 UI 中承诺 |
| 食品资料 | 已实现（有限） | 有来源和字段可用性；来源字段不足时需要确认 |
| 行动反馈 | 已实现 | complete/partial/not_done/unknown 均保留 |
| 个性化学习 | 部分实现 | 可生成需要用户确认的 evidence-only suggestion；不会自动写入长期偏好 |
| 热量/宏量营养素总量 | 不支持 | 餐名和可选份量不足以推导可信总量 |
| 菜谱级购物清单 | 不支持 | 目前只核对明确填写的主要食材、同名和相同单位 |

## 产品缺口与路线

| 优先级 | 缺口 | 依赖 | 建议下一步 |
|---|---|---|---|
| P0 | 过敏未知与安全评估的长期一致性 | Profile 迁移、食品来源字段 | 保持三态；为更多来源补齐可解释字段覆盖 |
| P1 | 选项与实际记录的稳定关联 | 用户确认的餐次/选项 ID | 在记录流程中提供可选关联，不自动猜测 |
| P1 | 多日计划编辑 | 日期级表单和冲突规则 | 先验证单日流程，再设计 7 日编辑器 |
| P1 | 行动反馈驱动的偏好确认 | 重复情境和用户确认 | 继续只输出建议，不自动改变 Profile |
| P2 | 成分级营养追踪 | 食谱/成分库、份量归一化、来源链 | 单独立项，先做覆盖率和未知值模型 |
